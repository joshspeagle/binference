The model object and its kernels

The code under everything: model.py (317 lines), _kernels.py (176) and _simplex.py (73). The math was step 2.1; this is how it is laid out, how fast it is, and what the model-map audit found.

§1

What a PopulationModel holds

AttributeWhat
likelihoodsthe user's Likelihoods (rows scaled to max 1, log-scales kept)
prior_spec, priorthe user's prior (default Dirichlet(1.0), D3) and its version bound to the bins
selection_spec, selection, selection_mode, _detectthe selection object, its values, its mode, and S/max S for imputation (2.4)
_Lthe effective matrix: columns × S for on-truth selection; otherwise the stored rows themselves (shared, not copied)
_w, W, _ll_constweights, their sum, and Σ wi log-scalei (restores absolute log-likelihoods)

Its methods come in three groups:

  • Unconstrained space (what NUTS, Laplace and L-BFGS see): log_prob_and_grad, log_prob, to_value, to_rho, transform, from_value.
  • Fraction/rate space: log_likelihood, log_prior, log_posterior, expected_counts, responsibilities, sample_prior, prior_transform, stack.
  • Diagnostics: kkt_gap, missing_information.

log_prob (in x, Jacobian included) and log_posterior (on the simplex) are different densities with similar names; this is exactly what #15 asks to make explicit.

§2

One evaluation of log_prob_and_grad(x)

  1. prior.forward(x) → logits η (fractions) or log-rates, plus a cache.
  2. value = softmax(η) or exp(η); non-finite → −∞.
  3. _ll_and_deta(value): the kernel's two passes over $L$ give $\ell$ and $\hat n$; then the selection or rate terms: $-W\log(S\cdot\rho)$ with $\hat n - W\rho S/(S\cdot\rho)$, or $-S\cdot\lambda$ with $\hat n - S\lambda$.
  4. prior.log_prior_and_grad(x, cache, value, d_eta): adds the prior density in x (Jacobian included) and chains $\partial\ell/\partial\eta$ back to x (for ILR: $V^{\top}(\cdot)$).
  5. Returns $\ell + \log p_x + $ _ll_const.

About a dozen lines; every gradient engine uses only this. Two notes:

  • Impossible objects. If any $L_i\cdot\rho \le 10^{-250}$ the whole evaluation is −∞ with a zero gradient. NUTS treats it as a divergence and rejects. The test counts every row, including rows with weight 0 (audit M-1).
  • transform(X) maps draws one at a time in Python. Fine for 4000 draws; worth vectorising for long runs and large K.
§3

The kernels, and how fast they are

_kernels.py · loglike_and_counts, responsibilities, sample_labels (dense / CSR), sample_counts
  • Likelihood + gradient: $s = L\rho$, $\ell = w\cdot\log s$, $\hat n = \rho\odot L^{\top}(w/s)$. Two reads of $L$, dense or CSR, no Python loop.
  • Responsibilities and label draws work in chunks of 65,536 rows. Dense labels use a per-row cumulative sum and one uniform per object; CSR labels normalise each row first and search one global cumulative sum (no per-row Python).
  • Counts with integer weights draw $\mathrm{Mult}(w_i, r_i)$ per compressed row.
N × Kdense float64implied bandwidthCSR (58% non-zero)
20,000 × 801.2 ms22 GB/s1.6 ms
200,000 × 10026 ms12 GB/s44 ms

One likelihood + gradient, single BLAS thread, this container. Gaussian rows with σ of about 1–8 bins (hence 58% non-zero after a 1e-8 cut). Script: experiments/2.6_kernel_speed.py.

What this means for "blazing fast" (#33):

  • The evaluation is memory-bound: its cost is reading $L$ twice. NUTS needs hundreds of evaluations per draw at large K, so at 10⁶ objects a run is minutes. The levers, in order: read $L$ once per evaluation (a fused kernel: about 2×), compress duplicate rows (already there), use several cores, and use a GPU (post-v1).
  • Sparse storage pays only when rows are mostly zero. At 58% non-zero it is slower than dense; from_samples switches at 30%. The threshold should come from a benchmark.
  • A dtype trap. A float32 matrix mixed with float64 vectors was 4–9× slower here (NumPy silently converts L on every call). With consistent float32 inputs it matched float64 speed in this container and halves memory. Likelihoods stores float64 today, so nobody hits the trap; a float32 option must keep every array in the same dtype.
§4

Simplex helpers

_simplex.py · helmert_basis (cached), softmax, log_softmax, clr, ilr, ilr_inv
  • The Helmert basis $V$ ($K\times(K-1)$, orthonormal, columns summing to zero) is built once per K and frozen.
  • Softmax and log-softmax subtract the maximum first; clr takes logs, so it needs strictly positive ρ (the samplers never produce exact zeros).
  • The Jacobian $\sqrt K\prod_k\rho_k$ is documented in the module docstring; the prior classes apply it (2.1 §7).
  • Parked from 2.1: tree-matched balance bases instead of Helmert for tree priors and many-empty-bin grids (3.1 / 4.2).
§5

The two diagnostics

kkt_gap(value)

With $G_k = \partial\log p/\partial\rho_k$ (likelihood, selection and, by default, prior), the gap is $\max_k(G_k - \rho\cdot G)/W$: zero at the optimum, and how far the best single-bin move would improve things otherwise (2.1 §6). Audit:

  • M-3: at a point where an object is impossible, the arithmetic produces NaN and Python's max(0.0, nan) returns 0.0, a false "optimal". Fix: return ∞ when any $L_i\cdot\rho = 0$.
  • M-4: for rates the gap has units of 1/λ, so the same 1% error reads 1.8e-8 or 1.8e-2 depending on the exposure's units. Fix: a relative form, $\hat n_k/(\lambda_k S_k) - 1$, the analogue of the fractions version.

missing_information(value)

The largest generalised eigenvalue of (missing information, complete information) in ILR coordinates, on at most 20,000 objects. It predicts EM's linear rate and the Gibbs autocorrelation, so it is a natural input to the adaptive engine choice (#14). Audit M-2: with selection it uses the wrong complete and observed information (0.50 where the true EM rate is 0.85), and it ignores the prior. The corrected formula (complete information $W/(S\cdot\rho)\,(\mathrm{diag}\,\rho-\rho\rho^{\top})$, observed $W(\mathrm{diag}\,\phi-\phi\phi^{\top}) - I_m$, plus the prior's $(A-K)(\cdot)$ term) matched the numerical EM rate to 4 decimals.

The model-map audit, in one place

The core math checks out everywhere (finite differences and brute-force optimisation to 1e-8). The findings are at the edges; all are fixed after the walkthrough (#13).

M-1Major. Rows with weight 0 still count in the impossibility test, so bootstrap EM resets to the prior mode or, for rates, to all zeros (79 of 200 replicates, silently)
