pastry walkthrough · Phase 1 · level L1–L2

What pastry is for

The problem, the scope and the design principles as written in the spec (§1–2), the README and the docs landing page, checked against what the code does and against the 32 decisions we've taken so far. Goal: agree on the vision and principles we'll hold the rest of the walkthrough (and the rewrite) to.

§1

The pitch, as written

Spec §1: pastry turns a catalogue of noisy, heteroscedastic, arbitrarily shaped per-object PDFs over a set of bins or categories into a posterior over the population distribution (fractions or rates), plus consistent posteriors for each object under that population.

"The baseline model has been implemented at least four times in astronomy alone … pastry's value is therefore usability, correct input conventions, calibrated uncertainty, validation and speed, not a new model."

The model itself is one line, $p(\rho\mid D) \propto p(\rho)\prod_i (L_i\cdot\rho)^{w_i}$ (step 2.1), and the census found it under five names: hierarchical n(z) / CMD inference in astronomy, iterative Bayesian unfolding in physics, NPMLE / g-modelling in statistics, EM quantification in machine learning, mixed-stock analysis in genetics.

Does the pitch still fit?

Mostly, but our decisions have moved pastry beyond "not a new model". Several are modelling contributions, not just usability:

  • Beyond flat-within-bin: B-spline mixture bases and internal resolution (#4, #5), with binning-bias diagnostics and a planner (#6, #20).
  • Auxiliary inputs inferred jointly: uncertain responses and selection functions as parameters (#28, #30), selection on truth and measurement at once (#8).
  • Inputs as estimators with error control: adaptive quadrature, the samples Monte Carlo check (#23, #31), the classifier routes and label-shift test (#29).
  • Adaptive defaults chosen from evidence, dynesty-style (#14).

Suggested rewrite of the last sentence: "pastry's value is correct input conventions, calibrated uncertainty, validation and speed, plus the pieces the existing implementations leave out: inputs whose own uncertainty is propagated, bases that remove the flat-within-bin approximation, and defaults chosen automatically."

§2

The design principles, checked

The spec lists six. Tap each for what the code does today and what our decisions changed. Filter:

1. Correct by construction strengthen

Says: the API makes users state likelihood or posterior, which interim prior, mass or density.

Today: mostly honoured (posteriors need an interim prior; array selections need a mode), but with holes: an interim array means mass in one constructor and density in another (I-1), from_function silently defaults to "likelihood", and "flat" doesn't say in which coordinate.

Decisions: #24, #26, #32 (one of kind/interim required; one density class; constructors named by input form), #15 (simplex vs unconstrained densities named explicitly), #21 (measure explicit).

2. Easy things one line, hard things possible holds

Says: pastry.infer on top; model and sampler objects below; raw log-densities for external samplers (as emcee, dynesty, nautilus, sbi).

Today: honoured: infer → PopulationModel + engine classes → log_prob_and_grad / prior_transform.

Decisions: #16 ("expose everything, with sensible defaults") is the same idea taken further: every tunable reachable. Open: the 1.3 architecture items (kwargs passthrough, closed method registry) bear on how "possible" the hard things are.

3. Exact by default; approximations labelled holds

Today: honoured: NUTS default; Laplace/VB/bootstrap carry approximate flags and an ApproximationWarning.

Nuance: "exact" is exact given the binned model. The flat-within-bin assumption (#5) and Monte Carlo inputs (#31) are approximations of the model itself and are not labelled today; the bias diagnostics (#6, #20) and the samples check (#31) extend the principle to them.

4. Self-validating extend

Today: R-hat/ESS/divergences computed automatically and check() called by infer for NUTS and Gibbs; SBC, coverage and exact quadrature posteriors ship in validation.

Decisions add checks of the inputs and model, not just the sampler: KKT gap (#12), binning bias (#6), mass outside the support (#18), samples Monte Carlo error (#31), label-shift test (#29), effective draws for selection (#30). Worth stating as part of the principle: pastry checks its sampler, its inputs and its approximations.

5. Lightweight core holds

Today: NumPy, SciPy and threadpoolctl (the spec says NumPy and SciPy only; threadpoolctl was added for the parallel-chains fix, a small text drift). Plotting and xarray are extras.

Decisions: #3 keeps NumPy gradients; JAX/PyTorch on the roadmap as an optional backend.

6. One result object drift

Says: every engine returns the same result type.

Today: not quite: MAP/EM returns a PointEstimate, the samplers a PopulationResult. They share the per-object methods (a mixin) but not summaries, intervals or functionals.

Options: fix the text ("one result type per kind of answer: draws or a point"), or make a point estimate a one-draw PopulationResult with a flag. To settle in Phase 5 (outputs).

7. Expose everything, sensible defaults new (#16)

Every tunable is reachable; nothing needs touching for a good result. Recorded per argument in the arguments ledger.

8. Adaptive, evidence-based defaults new (#14)

When the user doesn't choose, pastry chooses (engine, metric, basis, resolution) with every useful heuristic, as dynesty does, and says what it chose. Rules come from the benchmark matrix (4.6), not intuition.

9. The user's bins define the problem; internals adapt new (#17, #20, #21)

Arbitrary edges, N-D, masks and a measure; internal resolution and basis follow from the bins and the data. No data-driven re-binning by default.

10. Every uncertain input is modelled new (#10, #28, #30)

Selection functions, responses and calibration sets come with their uncertainty and are inferred jointly by default; fixing them is an explicit choice.

§5

Where README and docs will drift

Nothing to change yet (implementation comes after the walkthrough), but these front-page statements will become wrong, so they go on the Phase 8 list:

  • selection_mode="observed"/"true" → on_measurement/on_truth (#7), and combined selection (#8).
  • Constructor list (from_posteriors, from_function, from_distributions, from_response, from_classifier) → #32.
  • GammaRates as the way to get rates → #9.
  • "Dirichlet(alpha) is the default with alpha=1" → whatever the adaptive defaults decide (#14).
  • The model formula's weights $w_i$ → integer multiplicities in the public meaning (#1).
  • Spec §1 "NumPy and SciPy only" (threadpoolctl) and "one result object" (principle 6).
