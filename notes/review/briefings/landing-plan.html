Landing plan

How the v0.1 code, the walkthrough's 57 decisions and the audit's 127 findings reach main through issues and pull requests, modelled on telescopic's landing. Draft for your answers to the questions at the end.

§0

The shape

  • A tracking issue lists four phases as sub-issues; each phase issue lists its work issues.
  • One work issue per pull request, written before the code: scope, the decisions (#n) and audit findings (IDs) it resolves, acceptance criteria, records.
  • Pull requests are stacked: each branches from the previous one and is retargeted to main when that merges. Merge commits, so the commit hashes the notes cite stay valid.
  • At the end every decision so far and every audit finding is resolved on main, or is an open, well-specified issue labelled deferred. Walkthrough explainers stay in notes/review/, not issues.

§1

The loop for every pull request

  1. Write and link the issue.
  2. Branch land/NN-topic from the previous PR's branch; commits that each make one logical change.
  3. Fast tests, lint, format and the docs build pass locally (plus slow tests of changed modules).
  4. Open the PR; CI runs.
  5. /simplify, then /code-review, on the PR's diff, sized by lines changed: under 100 one reviewer (low effort); 100–500 two (medium); over 500 four (high); numerics or public API one size up. Fix valid findings, answer the rest in notes/pr-reviews/NN.md.
  6. CI green, merge, log entry, plan updated.

Independent PRs can be built in parallel worktrees while earlier ones are in review; merges stay in order.
