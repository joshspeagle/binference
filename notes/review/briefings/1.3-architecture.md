# Briefing 1.3: Architecture and data flow

*Goal of this step:* one mental picture of how a call travels from user input
to a result, which objects exist, what contract each one honours, and where
each concern lives. Everything in later phases hangs off this picture.

## 1. One call, end to end

```python
bins   = pastry.Bins.linear(0, 3, 30)                    # the support
lk     = pastry.Likelihoods.from_gaussian(z, sig, bins)  # data -> (N, K) matrix
result = pastry.infer(lk, priors.LogisticGP(), method="nuts")
result.summary(); result.assignment_probabilities()
```

What happens inside `infer` (`inference.py`, ~120 lines):

```
Likelihoods ──┐
Prior ────────┼──> PopulationModel ──> Engine(model).run(n) ──> PopulationResult
Selection ────┘     (prior.bind(bins))   NUTS/Gibbs/MAP/...      (or PointEstimate)
                                                                      │
                                                     result.check() ──┘ (warn on problems)
```

1. A `PopulationModel` is built from likelihoods + prior (+ optional selection).
   Building it *binds* the prior to the bins (`prior.bind(bins)` returns a
   `BoundPrior` with all the numerics).
2. `method` picks an engine class from a registry (`METHODS` dict). `"auto"`
   = NUTS unless more than 2e7 stored likelihood entries, then Laplace.
3. The engine is constructed with the model and engine-specific keywords
   (`**engine_kwargs` pass straight through), then `run(n_samples)`.
4. Sampling engines return a `PopulationResult` (draws); MAP returns a
   `PointEstimate`. For NUTS/Gibbs, `infer` calls `result.check()`.

So `infer` is a thin convenience layer. Everything it does can be done by hand
(spec §8.1 "layers"): build `PopulationModel` yourself, instantiate
`samplers.NUTS(model, ...)`, call `.run()` repeatedly to extend chains, etc.

## 2. The five core objects

| Object | File | Role | Key point |
|---|---|---|---|
| `Bins` | `bins.py` | The support: 1-D (linear/log/from centres), N-D grids (flattened to K cells), or unordered categories | Immutable and hashable. Knows edges, centres, **volumes**, neighbours, coarsening. Categories have no geometry. |
| `Likelihoods` | `likelihoods.py` | The data: an `(N, K)` matrix `L_ik ∝ p(d_i \| z_i ∈ B_k)` (dense or sparse) + bins + weights + optional `Selection` + `meta` | Rows stored **normalised to max 1**; per-row `log_scale` kept separately (only needed for absolute evidences). All conversions (posteriors, samples, Gaussians, functions, response matrices, classifiers) are `from_*` classmethods that end in this one representation. |
| `Prior` / `BoundPrior` | `priors/` | Configuration object the user writes / numerical object bound to specific bins | See §3. |
| `PopulationModel` | `model.py` | Likelihoods + bound prior + selection = the posterior. The only thing engines see. | Exposes `log_prob_and_grad(x)` in unconstrained space, plus fraction-space helpers (`log_likelihood`, `expected_counts`, `responsibilities`, `kkt_gap`, `missing_information`). |
| `PopulationResult` / `PointEstimate` | `results.py` | Draws (chains × draws × K) or a point, plus a reference to the model | Everything downstream (summaries, intervals, functionals, rebinning, per-object posteriors, predictive scores, diagnostics, plots, save/load) is computed from draws + model. |

Supporting pieces: `Selection` (`selection.py`, a tiny value object: per-bin
values + mode), engines (`samplers/`), `diagnostics.py` (pure functions on
arrays: R-hat, ESS, PSIS…), `validation.py` (exact posteriors, SBC, coverage),
`simulate.py` (mocks), `plotting.py`, `io.py`, `estimator.py` (sklearn-style
wrapper around `infer`).

## 3. The two contracts that make it pluggable

### Prior → BoundPrior (`priors/base.py`)

A `Prior` is just its parameters (what you type). `bind(bins)` validates them
against the bins and builds the numerics, e.g. the GP basis for that grid or
the tree structure for those bins. Every `BoundPrior` provides:

- **Unconstrained parametrisation**: `dim`, `forward(x) -> (eta, cache)` where
  `eta` are softmax logits (fractions) or log-rates (rates), and
  `log_prior_and_grad(x, cache, value, d_eta)` which returns the prior
  log-density *in x-space, Jacobian included*, and chains the likelihood
  gradient `d_eta` back to `x`.
  - Dirichlet family: `x` = isometric log-ratio (ILR) coordinates, `K-1` dims.
  - Logistic family: `x` = whitened field coefficients + log-hyperparameters.
  - Rates: `x` = log-rates.
- **Draws/densities** (where defined): `sample`, `log_density` on the simplex,
  `prior_transform` (for nested samplers), `unbounded_density()`.
- **Conjugate hooks** (Dirichlet family, Gamma rates only):
  `posterior_sample(counts)`, `map_from_counts(counts)`, `vb_*`. Flags:
  `conjugate`, `has_density`, `kind`.

Engines never ask "which prior is this"; they ask "is it conjugate / does it
have a density / what kind". (Two small exceptions: NUTS checks for
`with_centering` to apply partial non-centring to logistic priors, and MAP
checks for a Dirichlet `alpha` to use mix-SQP.)

### Engine (`samplers/base.py`)

`Engine(model, rng=, progress=, **options)`, `run(...)` → result. Engines
are stateful: NUTS keeps its chains, so `run()` again continues them.

| Engine | Needs | Returns | Exact? |
|---|---|---|---|
| `NUTS` | gradient (any prior) | `PopulationResult` | yes |
| `Gibbs` | conjugate prior, integer weights | `PopulationResult` (+ labels) | yes |
| `MAP` | any (algorithm chosen from prior) | `PointEstimate` | point |
| `Laplace` | gradient | `PopulationResult`, flagged approximate | approx. (PSIS-corrected) |
| `MeanFieldVB` | conjugate | `PopulationResult`, flagged | approx. |
| `Bootstrap` | MAP | `PopulationResult`, flagged | sampling distribution, not posterior |

## 4. The math that sits in the middle

`PopulationModel` evaluates (spec §3):

    log p(ρ|D) = log p(ρ) + Σ_i w_i log(L_i·ρ) − W log(S·ρ)        (fractions)
    log p(λ|D) = log p(λ) + Σ_i w_i log(L_i·λ) − S·λ               (rates)

and its gradient w.r.t. the logits, `n̂_k − W ρ_k S_k/(S·ρ)`, where
`n̂_k = ρ_k Σ_i w_i L_ik/(L_i·ρ)` are the expected counts (EM's E-step).
Everything expensive is two passes over `L` (`L ρ` and `Lᵀ(w/s)`), in
`_kernels.py`; this is why one gradient costs ~1 ms at N = 2×10⁴, K = 80.

Selection is folded in at model construction: in `"true"` mode the columns of
`L` are multiplied by `S` once (`model._L`); the normaliser term is added in
both modes. Rates use the same machinery with exposure instead of a normaliser.

## 5. Cross-cutting conventions worth knowing

- **value vs rho.** Internally "value" means fractions *or* rates depending on
  `model.kind` (set by the prior). `rho` always means fractions.
- **Weights.** Every object has a weight `w_i` (default 1). Integer weights are
  multiplicities (from `compress()`, unfolding counts), which Gibbs and the
  bootstrap rely on; non-integer weights give a weighted likelihood.
- **Normalised rows.** Row scales never matter for the population; storing
  `max = 1` rows avoids under/overflow, and `log_scale` restores absolute
  log-likelihoods when needed (`absolute=True`).
- **Randomness.** Every function takes `rng` (int / Generator / None, SPEC 7);
  chains get independent children of one `SeedSequence`.
- **Warnings as API.** `InputWarning` (suspicious inputs), `ConvergenceWarning`
  (diagnostics), `ApproximationWarning` (approximate engines). Tests run with
  warnings as errors.
- **No global state, NumPy/SciPy only** (+ `threadpoolctl`); matplotlib and
  xarray are optional extras.

## 6. Dependency structure (no cycles)

```
bins, selection, warnings, _utils, _simplex, diagnostics, plotting   (leaves)
   └─ likelihoods ─┐
priors (base → dirichlet / logistic / rates / hyper)
   └──────────────┴─ model ─ samplers (base → nuts/_nuts_core, gibbs, optimize, laplace, vb, bootstrap)
results (needs kernels, diagnostics; holds a model but does not import it)
inference (model + samplers + results) ─ estimator, validation, simulate
```

Engines import `results`; `results` deliberately does not import engines,
except lazily (`PointEstimate.laplace()`), and imports plotting/io lazily.

## 8. Decisions in this layer worth challenging

1. **Prior / BoundPrior split.** Pro: priors are cheap, printable config
   objects reusable across binnings; all bin-dependent numerics are computed
   once. Con: two classes per prior, and a "bound" concept users can see on
   `model.prior`.
2. **`PopulationModel` as a separate public object** between data and engines,
   rather than engines taking `(likelihoods, prior)` directly. It is what
   external samplers (emcee, dynesty, BlackJAX) use via `log_prob_and_grad`
   and `prior_transform`.
3. **Fractions vs rates chosen by the prior** (`GammaRates` → rates) rather
   than by a model flag. Compact, but "kind" is implicit.
4. **Selection lives in two places**: attachable to `Likelihoods` (adapters
   like `from_response` set it) and overridable on the model. Convenient for
   adapters; potentially confusing.
5. **`infer(method="nuts")` + `**engine_kwargs` passthrough** vs a more
   explicit API (e.g. `infer(..., engine=NUTS(...))` or method-specific
   option objects). Unknown keywords fail only inside the engine.
6. **Results hold the model** (so per-object methods work), which means saved
   results must be re-`attach`ed to likelihoods after loading.
7. **Flat module layout** (`pastry.Likelihoods`, `pastry.priors.X`,
   `pastry.samplers.X`) with `simulate`/`validation`/`diagnostics` as
   submodules. Naming: "samplers" also contains MAP and VB.
8. **The registry in `infer`** hard-codes the method names; a user-written
   engine cannot be plugged into `infer` without editing it.

## 9. Suggested reading order for the code (L2)

`inference.py` → `model.py` (top half) → `priors/base.py` → `samplers/base.py`
→ `likelihoods.py` (class docstring and `__init__` only) → `results.py`
(class outline). About 400 lines in total.
